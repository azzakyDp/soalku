# SoalKu Backend

Fondasi backend Java 21 dengan Maven multi-module dan Spring Boot 3.5.16.

## Struktur Step 1

```text
soalku-parent (pom.xml)
|-- core/          # Inti domain; belum memiliki dependency
|-- extraction/    # Modul ekstraksi dokumen
|-- persistence/   # Modul penyimpanan data
`-- web-api/       # Aplikasi Spring Boot; bergantung pada ketiga modul
```

Setiap modul memakai layout source Maven standar: `src/main/java`,
`src/main/resources`, `src/test/java`, dan `src/test/resources`.
Parent mengelola versi dependency dan target kompilasi Java 21.
Hanya `web-api` yang menggunakan plugin packaging Spring Boot.

## Build

Prasyarat: JDK 21 dan Maven 3.6.3 atau lebih baru. Arahkan `JAVA_HOME` ke JDK 21
dan tambahkan direktori `bin` Maven ke `PATH`.

Jalankan dari root project:

```shell
mvn validate
mvn clean install
```

Untuk mengompilasi `web-api` beserta dependency modulnya:

```shell
mvn -pl web-api -am compile
```

Setelah build, aplikasi dapat dijalankan dengan:

```shell
java -jar web-api/target/web-api-0.0.1-SNAPSHOT.jar
```

Aturan perubahan selanjutnya ada di `AGENTS.md`.

## Step 2 Koneksi PostgreSQL dan migrasi

Modul `persistence` menyediakan Spring Data JPA/Hibernate, driver PostgreSQL,
dan Flyway beserta dukungan PostgreSQL. `web-api` mengimpor konfigurasi dari
`soalku-persistence.properties`. Binding memakai `@ConfigurationProperties`
bawaan Spring Boot; tidak ada password bawaan atau kredensial di source.

Export variabel berikut melalui shell atau konfigurasi deployment:

| Variabel | Isi |
| --- | --- |
| `DB_URL` | JDBC URL, misalnya `jdbc:postgresql://localhost:5432/soalku` |
| `DB_USERNAME` | Akun database aplikasi |
| `DB_PASSWORD` | Password akun tersebut |

Contoh struktur variabel ada di `.env.example`. Menyalin file menjadi `.env`
saja tidak membuat Spring Boot memuatnya otomatis. Untuk Supabase, gunakan URL
JDBC dari konfigurasi koneksi project dan TLS sesuai konfigurasi penyedia;
jangan menaruh password pada URL atau source. Tidak ada koneksi otomatis ke
Supabase saat build atau test.

Untuk shell aplikasi Windows, simpan nilai lokal di `.env` (diabaikan Git), lalu:

```powershell
.\scripts\Import-SoalKuEnv.ps1
java -jar web-api/target/web-api-0.0.1-SNAPSHOT.jar
```

Script hanya mengekspor konfigurasi ke proses shell tersebut dan tidak mencetak
nilainya; Maven tidak mengimpor `.env`. URL session pooler Supabase memakai
format JDBC dengan `sslmode=require`, username/password terpisah. Pada startup
aplikasi, Flyway tetap menjalankan migrasi yang belum diterapkan; pemeriksaan
koneksi pada sesi Step 7 hanya membaca versi, tanpa menjalankan aplikasi ke Supabase.

Database harus sudah dibuat. Saat startup, Flyway membuat schema `soalku` dan
menerapkan `db/migration/V1__initial_schema.sql` sebelum Hibernate diinisialisasi.
Akun migrasi memerlukan hak membuat schema/tabel/index. Hibernate memakai
`ddl-auto=validate`; perubahan skema hanya melalui migrasi. JPA entity/repository
domain belum dibuat pada step ini, sehingga validasi mapping domain akan mulai
berlaku ketika entity ditambahkan. Open Session in View dimatikan.

Migrasi membuat sembilan tabel bisnis, masing-masing dengan `created_at`,
constraint, foreign key, dan index pendukung. `flyway_schema_history` adalah
tabel metadata tambahan milik Flyway, bukan tabel bisnis kesepuluh.
Log aplikasi memakai format JSON Logstash. Hikari memvalidasi koneksi database;
startup gagal jika konfigurasi, koneksi, checksum migrasi, atau validasi JPA gagal.
Step ini tidak menambah endpoint bisnis maupun endpoint health publik.

Keputusan skema:

- ID menggunakan `BIGINT GENERATED BY DEFAULT AS IDENTITY`; waktu menggunakan
  `TIMESTAMPTZ`, dengan Hibernate menyimpan waktu dalam UTC.
- Role hanya `SISWA` dan `MENTOR`, mengikuti spesifikasi role dan skema proposal.
  Status undangan adalah `AKTIF`, `DIGUNAKAN`, atau `DICABUT`.
- `materi.jenjang` menyimpan SD/SMP; `bagian_materi.teks_asli` menyimpan hasil
  ekstraksi; ringkasan boleh kosong sebelum generate; `soal.direview_at` mencatat
  waktu review. `urutan` dimulai dari 1.
- Email unik tanpa membedakan huruf besar/kecil. Opsi bernomor 1–4 dan maksimal
  satu kunci benar per soal. Jawaban harus merujuk opsi dari soal yang sama;
  pasangan sesi/soal unik untuk mencegah jawaban tersimpan ganda saat retry.
- Penghapusan memakai foreign key restriktif, tanpa cascade penghapusan data
  belajar. Pemeriksaan role pemilik/reviewer, jumlah tepat 3/4 opsi, dan kelayakan
  soal latihan tetap perlu diterapkan pada step layanan domain terkait; skema
  awal belum mengimplementasikan layanan tersebut.

### Pengulangan dan kegagalan migrasi

Jalankan `migrate` melalui startup aplikasi seperti biasa. Flyway memeriksa
checksum dan history sehingga startup/migrate berikutnya tidak membuat ulang
objek atau menghapus data. DDL PostgreSQL dijalankan dalam satu transaksi;
kegagalan membatalkan seluruh V1 sehingga dapat dicoba lagi.

Jangan menjalankan ulang fragmen SQL secara manual atau mengubah V1 setelah
diterapkan. `CREATE TABLE` sengaja tidak memakai `IF NOT EXISTS`, agar skema
yang berbeda tidak dianggap benar secara diam-diam. Idempotensi berada pada
operasi Flyway `migrate`; eksekusi manual berulang dalam transaksi gagal tanpa
merusak data. Migrasi ini hanya membuat tabel baru dan tidak melakukan ALTER
atau backfill pada tabel besar. Batas tunggu lock adalah 3 detik.

### Rollback V1

`db/rollback/U1__initial_schema.sql` adalah rollback manual untuk Flyway Community,
bukan migrasi startup dan bukan klaim dukungan perintah `flyway undo`.

Hentikan instance aplikasi/penulis data. Pastikan database dan schema yang dipilih
benar. Jalankan dengan akun migrasi dari root project menggunakan koneksi `psql`
yang disediakan di environment; `PGPASSWORD` tidak ditulis dalam command:

```shell
psql -v ON_ERROR_STOP=1 -c "SET search_path TO soalku" -f persistence/src/main/resources/db/rollback/U1__initial_schema.sql
```

`psql` membaca `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, dan `PGPASSWORD`;
`DB_URL` dalam format JDBC tidak dibaca oleh `psql`.

Rollback bersifat transaksional, membatasi waktu tunggu lock, menolak tabel
berisi data, menolak history migrasi lebih baru/tabel asing, dan menghapus tabel
kosong dalam urutan terbalik tanpa `CASCADE`. History versi 1 dihapus dalam
transaksi yang sama agar startup berikutnya dapat menerapkan V1 lagi. Schema
dan metadata history lainnya dipertahankan. Skrip aman diulang pada schema
kosong. Jangan menjalankannya bersamaan dengan migrasi/startup aplikasi.

Untuk database yang sudah berisi data, rollback struktural ini sengaja berhenti:
gunakan backup terverifikasi dan rencana restore yang disetujui, bukan menghapus
data secara otomatis.

### Integration test PostgreSQL

Test tidak menggunakan mock/H2 dan tidak berjalan pada Supabase. Siapkan database
testing lokal dengan nama berakhiran `_test` dan akun yang boleh membuat schema.
Export `SOALKU_TEST_DATABASE_URL` (misalnya
`jdbc:postgresql://127.0.0.1:5432/soalku_test`),
`SOALKU_TEST_DATABASE_USERNAME`, dan `SOALKU_TEST_DATABASE_PASSWORD`.

```shell
mvn -pl persistence -am -Ppostgres-it verify
```

Profile `postgres-it` menjalankan integration test lewat Failsafe. Tanpa profile
tersebut, build biasa tidak memerlukan server database; itu tidak berarti
integration test sudah dijalankan. URL testing dibatasi ke localhost/127.0.0.1
dengan port eksplisit dan nama database `_test`, tanpa query parameter. Setiap
test memakai schema acak `soalku_it_*` dan menghapus hanya schema miliknya.

Test mencakup migrate dua kali, sembilan tabel dan timestamp, constraint data,
rollback dua kali lalu migrate ulang, penolakan rollback terhadap data/migrasi
lebih baru, kegagalan DDL di tengah transaksi, serta koneksi Hibernate melalui
konfigurasi Spring Boot. Pengujian lokal dilakukan pada PostgreSQL 18.4; versi
Flyway yang dikelola parent Spring Boot memberi peringatan bahwa dukungan yang
diujinya sampai PostgreSQL 17. Ketujuh test lulus, tetapi untuk deployment pilih
versi PostgreSQL yang didukung stack tersebut atau evaluasi upgrade secara
terpisah sebelum memakai PostgreSQL 18.

## Step 3 Autentikasi

API memakai bcrypt dengan cost 12 dan JWT HS256 melalui Spring Security/Nimbus.
Tidak ada dependency Spring pada `core`; enum `Role` berada di `core`, mapping
akun/undangan di `persistence`, dan kontrak HTTP serta keamanan di `web-api`.
Tidak diperlukan perubahan skema atau migrasi baru untuk step ini; V1 tetap utuh.

Tambahkan environment variable:

| Variabel | Isi |
| --- | --- |
| `JWT_SECRET` | Base64 dari minimal 32 byte acak kriptografis; wajib, tanpa default |
| `JWT_ISSUER` | Issuer token, default `soalku` |
| `JWT_TTL` | Masa berlaku token, default `15m`, dibatasi 1 detik sampai 1 jam |

Contoh membuat secret di PowerShell dan langsung memasangnya ke environment tanpa
mencetak atau menyimpannya ke file:

```powershell
$jwtBytes = New-Object byte[] 32
$jwtRng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$jwtRng.GetBytes($jwtBytes)
$jwtRng.Dispose()
$env:JWT_SECRET = [Convert]::ToBase64String($jwtBytes)
```

Gunakan secret yang sama di semua instance aplikasi. Untuk deployment, simpan
secret secara persisten melalui konfigurasi runtime; contoh di atas membuat nilai
baru setiap kali dijalankan, sehingga token lama tidak lagi valid setelah rotasi.

| Endpoint | Akses | Hasil |
| --- | --- | --- |
| `POST /api/auth/register` | Publik | `201` dan identitas akun tanpa password/hash |
| `POST /api/auth/login` | Publik | `200`, `accessToken`, `tokenType: Bearer`, `expiresIn` dalam detik |
| `GET /api/auth/me` | Bearer JWT valid | Identitas akun berdasarkan subject token; tidak menerima ID pengguna lain |
| `GET /actuator/health` | Publik | Status kesehatan termasuk koneksi DB, tanpa detail konfigurasi |

Contoh body register Siswa:

```json
{
  "nama": "Siswa Demo",
  "email": "siswa@example.test",
  "password": "contoh-password-aman",
  "role": "SISWA"
}
```

Untuk Mentor, kirim `role: MENTOR` dan `kodeUndangan` yang valid. Siswa tidak
memerlukan kode dan tidak boleh mengirim kode nonkosong. Password registrasi
minimal 8 karakter dan maksimal 72 byte UTF-8 agar tidak terpotong oleh bcrypt.
Email dinormalisasi ke huruf kecil. Field JSON yang tidak dikenal ditolak,
termasuk upaya mengirim `passwordHash` atau atribut internal JPA.

Body login berisi `email` dan `password`. Kirim token hanya melalui header
`Authorization: Bearer <accessToken>`. Token berisi `sub` berupa ID akun,
`role`, `iss`, `aud: soalku-api`, `iat`, `exp`, dan `jti`. Decoder hanya menerima
HS256, memverifikasi signature, issuer, audience, waktu berlaku, serta role
SISWA/MENTOR. Token, password, hash, dan kode undangan tidak dicatat ke log.

Setiap request mendapat header respons `X-Request-ID`. Header masuk hanya dipakai
jika terdiri dari 1–64 karakter huruf/angka ASCII, titik, garis bawah, atau tanda
minus; nilai lain diganti UUID. Log terstruktur memuat `request_id` melalui MDC
serta event penyelesaian berisi method, pola route, status, dan `duration_ms`.
MDC dipulihkan setelah request selesai; body, query string, token, serta path
tak dikenal tidak dicatat. Test memverifikasi korelasi untuk respons 200/401/400
dan memastikan input sensitif tidak ikut tercatat.

Autentikasi memverifikasi identitas dari token; otorisasi menerjemahkan claim
`role` menjadi `ROLE_SISWA` atau `ROLE_MENTOR`. Method security aktif; endpoint
khusus Mentor juga dapat memakai `@PreAuthorize("hasRole('MENTOR')")`
untuk perlindungan di level method. Route Mentor untuk pengujian hanya ada di source test,
bukan bagian API produksi. Akses tanpa token/token tidak valid mendapat `401`,
sedangkan role yang tidak diizinkan mendapat `403`. Session, form login, dan
HTTP Basic dimatikan; CSRF dimatikan untuk API stateless yang memakai bearer
header dan tidak memakai autentikasi cookie.

Kode Mentor harus berstatus `AKTIF`, `expired_at` harus lebih besar dari waktu
UTC sekarang, dan pembuatnya harus Mentor. Pendaftaran dan perubahan status
menjadi `DIGUNAKAN` dilakukan dalam satu transaksi dengan row lock. Dua request
bersamaan tidak dapat memakai kode yang sama. Kode invalid, kosong, kedaluwarsa,
dicabut, atau sudah dipakai menghasilkan `400`; email duplikat menghasilkan
`409` tanpa membuat akun kedua atau mengonsumsi kode tambahan. Retry register
tidak menduplikasi akun; respons retry atas akun yang sudah terdaftar adalah
`409`, bukan replay respons `201`. Login yang salah memakai pesan `401` yang
sama untuk email tidak dikenal dan password salah.

Akun Mentor pertama dan kode awal tetap dibuat **manual melalui seed database**
sesuai PRD. Seed harus mengisi `pengguna` dengan role `MENTOR` dan password hash
bcrypt yang valid, kemudian `kode_undangan` dengan `dibuat_oleh` merujuk Mentor
tersebut, status `AKTIF`, dan `expired_at > created_at`. Tidak ada password,
akun demo, kode undangan bawaan, atau jalur registrasi Mentor tanpa kode.
Endpoint pembuatan kode baru dan fitur bisnis lainnya belum ditambahkan.

Untuk verifikasi seluruh modul, termasuk test HTTP autentikasi dengan PostgreSQL
testing yang sama seperti Step 2:

```shell
mvn -Ppostgres-it verify
mvn validate compile
```

Test menggunakan filter Spring Security sebenarnya, bcrypt, JWT bertanda tangan,
dan PostgreSQL nyata. Cakupannya meliputi kode invalid/expired/dicabut/terpakai,
pendaftaran dua role, transaksi dan konsumsi kode bersamaan, login, claim JWT,
token palsu/expired, `401`/`403`, mass assignment, batas byte bcrypt, serta health DB.
Unit test juga menolak secret JWT dan masa berlaku token yang tidak valid.

## Step 4 RBAC pada filter request

Namespace `/api/mentor` dan `/api/mentor/**` khusus role `MENTOR` untuk semua
HTTP method. Endpoint khusus Mentor pada step berikutnya harus ditempatkan di
namespace ini; jika memakai path lain, tambahkan aturan role eksplisit sebelum
aturan akses umum. Endpoint review dan pengelolaan bank soal belum dibuat.

Alur guard memakai komponen standar Spring Security:

1. `BearerTokenAuthenticationFilter` memverifikasi JWT melalui decoder Step 3.
2. Claim `role` yang sudah tervalidasi diubah menjadi authority `ROLE_SISWA`
   atau `ROLE_MENTOR`.
3. `AuthorizationFilter` menerapkan `hasRole("MENTOR")` pada namespace Mentor
   sebelum meneruskan request ke controller.

JWT SISWA yang valid mendapat `403` dengan kode error `FORBIDDEN`; token tidak
ada/tidak valid/kedaluwarsa mendapat `401`. JWT MENTOR yang valid melewati guard,
lalu mengikuti perilaku endpoint yang dituju. Error tetap memiliki request ID
dan tercatat pada log terstruktur. Detail signature, token, dan kredensial tidak
dikembalikan pada respons error. Health DB dari Step 3 tetap tersedia.

Test eksplisit `siswaJwtGets403BeforeUnannotatedMentorControllerRuns` memakai
token hasil register/login nyata dan endpoint fixture **tanpa `@PreAuthorize`**.
Test memeriksa GET/POST pada root namespace, satu path anak, dan path bertingkat;
seluruhnya harus `403`, dan penghitung pemanggilan controller harus tetap nol.
Test pendamping memastikan MENTOR mendapat `200` pada fixture yang sama serta
token tidak ada/kedaluwarsa mendapat `401` tanpa memanggil controller. Fixture
dan penghitung hanya berada di source test dan tidak masuk JAR aplikasi.

Jalankan `mvn -Ppostgres-it verify` untuk seluruh test dengan PostgreSQL testing,
kemudian `mvn validate compile` untuk verifikasi build.

## Step 5 Upload dan ekstraksi materi

`POST /api/materi/upload` menerima multipart `file`, `judul` (wajib, maksimal
255 karakter), dan `jenjang` (`SD`/`SMP`). Gunakan bearer JWT role `SISWA`;
tanpa JWT mendapat `401`, role MENTOR mendapat `403`. Pemilik selalu berasal
dari `sub` JWT dan diverifikasi kembali terhadap akun di database.

```shell
curl -X POST http://localhost:8080/api/materi/upload \
  -H "Authorization: Bearer <accessToken>" \
  -F "file=@pelajaran.pdf" -F "judul=Ilmu Alam" -F "jenjang=SD"
```

Format yang didukung adalah PDF dan DOCX, maksimal **10 MiB** (10 × 1024 × 1024
byte). Batas multipart diterapkan oleh server dan diperiksa lagi sebelum parser.
Ekstensi dan isi dokumen diperiksa; MIME kiriman klien tidak dijadikan bukti
format. File asli disimpan bersama gambar PNG hasil ekstraksi di direktori privat
`MATERIAL_STORAGE_ROOT` (default `./data/materials`). Gunakan volume persisten
yang hanya dapat ditulis proses aplikasi; jangan sajikan direktori ini sebagai
static web root. Nama berkas/path dari klien dan nama entri ZIP tidak dipakai
sebagai tujuan penulisan. Path relatif disimpan ke database; respons tidak
membocorkan path fisik server. Backup database dan volume berkas sebagai satu kesatuan.

DOCX dipisah pada style `Heading1`–`Heading9`, `Title`, atau outline level;
teks tabel ikut diekstrak. PDF memakai ukuran huruf relatif dan pola judul Bab
untuk mengenali heading, dengan fallback per halaman. Pengelompokan PDF bersifat
heuristik; tata letak multi-kolom/rotasi kompleks dapat memerlukan koreksi pada
step pengeditan materi. Gambar raster tertanam disimpan terpisah dan setiap baris
`gambar_materi` merujuk `materi_id` serta `bagian_materi_id` yang sesuai.
Gambar DOCX tanpa posisi paragraf yang tersedia ditempatkan di bagian terpisah
dengan peringatan. Vector drawing bukan gambar raster; OCR tidak diimplementasikan.
PDF scan tanpa teks mengembalikan peringatan dan tetap menyimpan gambar.

Parser membatasi PDF 200 halaman, 200 bagian, 200 gambar, 1 juta karakter,
10 juta pixel/gambar, dan 25 MiB total PNG. Isi ZIP DOCX setelah ekspansi dibatasi
50 MiB/2000 entri; stream non-gambar PDF dibatasi 16 MiB per tahap decode dan
50 MiB total. PDF terenkripsi dan gambar yang tidak dapat dibaca ditolak secara
jelas. Batas ini mencegah akumulasi hasil tanpa batas; kapasitas heap dan batas
request serentak tetap harus disesuaikan saat deployment.

Respons awal `201` memuat ID materi, judul, jenjang, bagian berurutan, referensi ID
gambar, dan peringatan. Teks asli masuk `bagian_materi.teks_asli`;
`teks_ringkasan` tetap NULL. Tidak ada pemanggilan AI dalam step ini.
Retry dengan **owner, byte file, judul yang sudah di-trim, dan jenjang sama**
mengembalikan materi yang sama dengan `200` dan `duplikat: true`. Perbedaan nama
file klien tidak membuat duplikasi. Row lock akun menyerialkan finalisasi per
pemilik; unique index `materi.file_path` menjadi perlindungan database.
Query respons mengambil semua bagian dan gambar materi secara terpisah dengan
jumlah query konstan; tidak ada relasi eager atau endpoint daftar tanpa pagination.

Berkas ditulis ke staging, dipindah atomik di volume yang sama, lalu tiga tabel
disimpan dalam satu transaksi. Rollback terkonfirmasi menghapus berkas baru.
Jika hasil commit tidak diketahui, berkas dipertahankan dan event
`material.commit_unknown` dicatat agar retry/reconciliation tidak kehilangan aset.
Orphan identik akibat proses mati sebelum commit dapat dipakai kembali oleh
retry; berkas bertentangan menghasilkan `409`, tidak ditimpa. Cleanup gagal
dicatat dan perlu ditindaklanjuti pengelola. Tidak ada janji transaksi atomik
lintas filesystem dan PostgreSQL saat proses/mesin mati.

Error JSON memakai `code` dan `message`: metadata/file kosong `400`, format
tidak didukung `415`, file terlalu besar `413`, file rusak/terenkripsi atau
batas ekstraksi `422`, dan penyimpanan gagal `500`. Log terstruktur mencatat
request ID, hasil, jumlah bagian/gambar, dan kategori kegagalan; isi dokumen
tidak dicatat. `/actuator/health` memeriksa DB dan kemampuan tulis/baca/hapus
penyimpanan privat, sementara respons publik tetap hanya status kesehatan.

V2 menambah unique index secara `CONCURRENTLY`, tanpa mengubah V1 atau menghapus
data. Flyway memakai session advisory lock (`transactional-lock=false`) untuk
menghindari deadlock saat index concurrent dibuat. Riwayat Flyway membuat
migrate ulang menjadi no-op. Bila build index gagal (misalnya data lama memiliki
path duplikat), selesaikan konflik data secara terencana, jalankan `flyway repair`
dengan konfigurasi schema yang sama, lalu migrate lagi; script membersihkan index
gagal sebelum membangunnya kembali. Rollback manual
`db/rollback/U2__unique_material_file_path.sql` dijalankan pada search_path schema
SoalKu yang benar **tanpa transaction wrapper**, saat upload dihentikan sementara.
Rollback dapat diulang dan mempertahankan semua baris; rollback V2 sebelum V1.

Verifikasi: `mvn -Ppostgres-it verify`, lalu `mvn validate compile`. Test menggunakan
PDF/DOCX hasil library asli, PostgreSQL testing terisolasi, filter JWT sebenarnya,
dan filesystem nyata untuk retry serentak, pemisahan owner, akses ditolak,
error dokumen, health storage, serta kompensasi saat database menolak insert.

## Step 6 Generate ringkasan dan soal melalui Gemini

### Isolasi test otomatis dan smoke manual

Test Maven tidak menghubungi Google. Test orkestrasi `MaterialGenerationMockIT`
memakai mock `QuestionGeneratorService` dengan transaksi PostgreSQL nyata;
test adapter memakai server HTTP loopback dan respons JSON fixture. Seluruh
Spring integration test memakai profile `test`, yang memaksa key kosong dan
endpoint loopback port 9, meskipun CI/developer sudah mengekspor key Gemini.
Hanya test adapter/integrasi HTTP yang secara eksplisit mengganti endpoint itu
dengan server lokal yang dibuat test. Tidak ada credential Gemini asli pada
source test; keluaran/assert bersifat deterministik dan tidak memakai kuota API.

Satu smoke manual tersedia di `scripts/Invoke-GeminiSmoke.ps1`, di luar source,
profile dan lifecycle Maven. Jalankan aplikasi lokal dengan key pada environment,
unggah fixture nonsensitif milik akun penguji, set `SOALKU_SMOKE_TOKEN` dan
`SOALKU_SMOKE_MATERIAL_ID`, lalu panggil secara eksplisit:

```powershell
./scripts/Invoke-GeminiSmoke.ps1 -ConfirmPaidCall
```

Script menolak jalan tanpa switch tersebut dan hanya menerima server loopback.
Ia tidak dijalankan oleh `mvn test`, `verify`, `clean install`, atau hook Git.
Uji live pada sesi sebelumnya adalah verifikasi manual terpisah, bukan test CI.

### PostgreSQL dan build Windows

Versi Supabase sudah diperiksa secara read-only: **PostgreSQL 17.11**. Testing
lokal memakai PostgreSQL 18.4/Flyway 11.7.2 dan masih mempunyai risiko perbedaan
major dengan produksi. Ulangi suite pada PostgreSQL 17 terisolasi sebelum deploy.

Konfigurasi tambahan: `GEMINI_MODEL` (default `gemini-3.8-flash`),

Klien memakai JDK HttpClient, hanya endpoint resmi HTTPS Google; URL loopback
HTTP diizinkan khusus konfigurasi test. Redirect tidak diikuti agar header key
tidak diteruskan ke host lain.

Setelah upload selesai, panggil **`POST /api/materi/{id}/generate`**, tanpa body,
dengan bearer JWT SISWA pemilik materi. Upload tetap merupakan operasi terpisah:
kegagalan generate tidak membatalkan materi/bagian/gambar yang sudah tersimpan.
Tanpa autentikasi mendapat `401`, MENTOR `403`, dan materi milik siswa lain `404`.

`QuestionGeneratorService` berada di `core` tanpa dependensi Spring/UI/provider.
`GeminiGeneratorService` di `web-api` mengimplementasikan port tersebut.
Setiap bagian dikirim sebagai satu chunk utuh menggunakan kerangka prompt PRD 7:
ringkasan maksimal lima kalimat, N soal, dan 3 opsi SD atau 4 opsi SMP. Gambar
PNG bagian tersebut disertakan sebagai inline data dengan ID yang boleh dirujuk.
Materi diperlakukan sebagai data, bukan instruksi untuk mengganti tugas/schema.
Bagian tanpa teks (misalnya scan yang membutuhkan OCR) atau di atas 50.000
karakter mendapat `422`; teks tidak dipotong diam-diam. Total PNG untuk AI
dibatasi 10 MiB per bagian.

JSON diminta melalui `generationConfig.responseFormat.text` dengan
`mimeType: APPLICATION_JSON` dan schema, sesuai
[referensi REST Gemini](https://ai.google.dev/api/generate-content#TextResponseFormat).
Parser lokal tetap memvalidasi field wajib/asing, duplicate JSON keys, trailing
content, hasil lengkap `STOP`, jumlah soal/opsi, teks, satu kunci benar, opsi dan
pertanyaan duplikat, serta referensi gambar yang benar-benar berasal dari bagian
tersebut. `jawaban_benar` memakai nomor opsi mulai 1; `gambar_id` integer atau
null. Hasil baru selalu `MENUNGGU`, tanpa reviewer/waktu review. Alur persetujuan
Mentor ditambahkan pada Step 7 di bawah.

Ringkasan ditulis ke `bagian_materi.teks_ringkasan`; setiap `Soal` dan
`OpsiJawaban` disimpan dalam transaksi yang sama dengan penanda `generated_at`.
Jika transaksi gagal, seluruh hasil bagian itu di-rollback. Hasil bagian lain
yang sudah selesai tetap tersimpan. Response memuat `materiId`, `selesai`, dan
`bagian[]` berisi ID bagian, status, ringkasan, ID soal, serta code/message bila
gagal; kunci jawaban tidak dikirim dalam response endpoint generate.

Idempotency berlaku **per bagian**: retry mengembalikan `SUDAH_ADA` beserta ID
soal lama untuk bagian yang sudah selesai, tanpa memanggil Gemini lagi. Jumlah
soal/model baru dari konfigurasi tidak otomatis mengganti hasil yang selesai.
Bagian baru diklaim lewat row lock singkat dan UUID lease selama dua menit.
Network call berjalan di luar transaksi database. Finalisasi memeriksa UUID;
writer lama tidak boleh menimpa hasil atau melepas lease milik request baru.
Lease proses yang mati dapat diambil kembali setelah kedaluwarsa. Unique index
`(bagian_materi_id, urutan_generasi)` mencegah penyimpanan set soal ganda.
Timeout transaksi/statement 5 s dan lock wait 2 s membatasi penantian database.

Client membatasi empat panggilan Gemini serentak per instance, body respons
512 KiB saat diterima, dan deadline HTTP mencakup pembacaan body. Tidak ada retry
provider otomatis yang dapat menghabiskan kuota tanpa terlihat. Batch memiliki
budget 55 s untuk memulai pemrosesan; bila habis, retry melanjutkan bagian yang
belum selesai. Waktu finalisasi/cleanup database dapat menambah beberapa detik.
Query gambar diambil sekali per materi lalu dikelompokkan; transaksi dan query
soal per bagian memang disengaja untuk checkpoint hasil yang independen. List
dibatasi batas ekstraksi (200 bagian/200 gambar, maksimal 10 soal per bagian).

Saat gagal, HTTP dapat berupa `409` (bagian sedang diproses/lease berganti),
`422` (input belum bisa diproses), `502` (hasil AI tidak valid), `503`
(konfigurasi, provider/kuota, atau database sibuk), `504` (timeout), atau `500`
(hasil tidak berhasil disimpan). Baca setiap hasil bagian: response gagal dapat
tetap memuat bagian yang sudah sukses. Retry endpoint yang sama aman terhadap
duplikasi database. Jika Google sudah memproses request tetapi koneksi/commit
terputus sebelum hasil diketahui, request provider mungkin diulang saat retry;
API provider tidak menjamin exactly-once billing. Hasil database tetap dilindungi
transaksi, penanda completion, unique index, dan fencing lease.

Log terstruktur mencatat event, request ID, ID materi/bagian, durasi, dan kategori
kegagalan, tanpa key, prompt, gambar, atau hasil AI. Pesan exception SQL mentah
dapat memuat isi row, sehingga logger Hibernate tersebut dimatikan; handler
generate mencatat SQL state, jenis exception, dan stack yang sudah disanitasi.
Health Gemini memakai status konfigurasi dan hasil panggilan nyata terakhir
(`UNKNOWN` sebelum panggilan/key belum diatur, `UP` sesudah sukses, `DOWN` sesudah
gagal), tanpa panggilan berbayar dari probe. Health publik tetap menyembunyikan
detail. Saat provider gagal, health agregat dapat `DOWN`; data materi tetap utuh.

V3 hanya menambah kolom nullable, constraint generation state, urutan soal, unique
index concurrent, dan FK gambar yang membatasi gambar soal ke bagian asalnya.
DDL memakai lock timeout 3 s, index `CONCURRENTLY`, dan validasi constraint
terpisah dari penambahan metadata. Tidak ada penghapusan/backfill materi.
Flyway migrate ulang menjadi no-op; script juga diuji dapat diterapkan kembali
pada schema yang sudah memiliki kolom/index/FK V3 untuk pemulihan partial apply.
Jika V3 gagal, perbaiki penyebab dan jalankan Flyway repair/migrate pada schema
yang sama. Rollback manual `db/rollback/U3__generation_state.sql` dijalankan saat
generate dihentikan, setiap statement terpisah tanpa transaction wrapper.
Rollback dapat diulang, tetapi menolak metadata generation yang masih digunakan
agar completion/idempotency tidak hilang. Ekspor/pulihkan metadata melalui
rencana pemeliharaan sebelum rollback schema yang sudah menghasilkan soal.

Verifikasi: `mvn -Ppostgres-it verify` dan `mvn validate compile`. Unit test
memakai server HTTP lokal dengan client/parser nyata. Integration test memakai
PostgreSQL testing, filesystem, JWT, upload DOCX, dan endpoint nyata melalui
MockMvc: dua jenjang, hasil parsial/retry, ownership/role, API error, timeout,
lease kedaluwarsa/writer lama, retry serentak, rollback hasil, dan row lock yang
ditahan koneksi lain. Pengujian otomatis tidak memakai key/kuota Gemini asli.
Uji live memakai key dari environment dan hanya materi fixture nonsensitif;
verifikasi manual oleh anggota tim lain sesuai PRD tetap perlu dilakukan tim.

## Step 7 Review Soal oleh MENTOR

Semua endpoint berikut memerlukan bearer JWT MENTOR. JWT memverifikasi identitas,
filter `/api/mentor/**` membatasi role sebelum controller, dan service memeriksa
bahwa akun masih berstatus MENTOR di database. Tanpa token mendapat `401`, SISWA
`403`. Sesuai PRD 2/F4, Mentor mereview antrean global dari seluruh materi siswa;
belum ada relasi penugasan Mentor–Siswa dalam skema. Kunci jawaban pada response
review hanya tersedia dalam namespace khusus MENTOR.

| Method | Endpoint | Perilaku |
| --- | --- | --- |
| GET | `/api/mentor/soal?page=0&size=20` | Daftar hanya `MENUNGGU`, lengkap dengan opsi, urutan `created_at,id` naik |
| PUT | `/api/mentor/soal/{id}` | Ganti teks pertanyaan dan seluruh isi/kunci opsi pada soal yang masih menunggu |
| POST | `/api/mentor/soal/{id}/approve` | Tetapkan `DISETUJUI`; tanpa body |
| POST | `/api/mentor/soal/{id}/reject` | Tetapkan `DITOLAK`; tanpa body |

Pagination berbasis nol, size 1–100 dan page 0–1000000. Response daftar memiliki
`content`, `page`, `size`, `totalElements`, dan `totalPages`. Daftar kosong tetap
`200`. Pertanyaan memuat `id`, `bagianMateriId`, `pertanyaan`, `gambarId`,
`statusReview`, `direviewOleh`, `direviewAt`, `createdAt`, serta `opsi` berurutan.
Query menggunakan index status/created yang sudah ada dan satu bulk query opsi
untuk satu halaman, tanpa eager collection atau N+1.

Contoh body PUT untuk SMP (gunakan ID opsi dari response daftar):

```json
{
  "pertanyaan": "Apa fungsi utama akar?",
  "opsi": [
    {"id": 101, "teks": "Menyerap air dan mineral", "benar": true},
    {"id": 102, "teks": "Menghasilkan bunga", "benar": false},
    {"id": 103, "teks": "Membentuk buah", "benar": false},
    {"id": 104, "teks": "Menyebarkan biji", "benar": false}
  ]
}
```

Tepat 3 opsi SD atau 4 opsi SMP, satu kunci benar, seluruh ID unik dan harus
milik soal tersebut. ID/urutan opsi dipertahankan; ID lintas soal ditolak. Opsi
tidak boleh mempunyai teks identik setelah trim/normalisasi huruf kecil. Teks
tidak boleh kosong (pertanyaan maksimal 3000 karakter, opsi 1000); field asing
termasuk status/reviewer dari klien ditolak. Tidak ada pengubahan gambar,
pemilik materi, tipe soal, atau jumlah opsi melalui endpoint edit ini.

Edit mempertahankan `MENUNGGU` dan audit final tetap null sesuai constraint
`ck_soal_review`. Event edit mencatat ID Mentor/soal pada log terstruktur.
Approve/reject mencatat `direview_oleh` dari identitas JWT dan `direview_at` dari
Clock server UTC dalam transaksi yang sama. Keputusan final tidak dapat dibalik
atau diedit: `409`. Pengulangan keputusan yang sama mengembalikan hasil tersimpan
tanpa mengganti reviewer/waktu, termasuk retry oleh Mentor lain. PUT berulang
dengan isi sama mempertahankan ID opsi tanpa menggandakan data.

Row lock per soal menserialisasi edit/keputusan yang bersamaan. Pergantian kunci
melepas kunci lama terlebih dahulu, lalu menetapkan kunci baru dalam satu transaksi
agar unique index kunci tidak bentrok. Kegagalan menulis opsi me-rollback seluruh
perubahan. Lock timeout 2 detik dan timeout transaksi/statement 5 detik membatasi
penantian. `400` untuk input/parameter/opsi tidak valid, `404` untuk soal hilang,
`422` jika soal tidak mempunyai opsi/kunci valid saat approve, `503` untuk
database sibuk (retry diperbolehkan), `500` bila penyimpanan gagal. Detail SQL/isi
soal tidak dibocorkan melalui response/log. Health memakai pemeriksaan database
Actuator yang sudah tersedia; tidak menambah dependency atau migrasi schema.

Integration test `QuestionReviewIT` memakai JWT, filter, service, JPA, Flyway,
dan PostgreSQL testing nyata: batas role, input, antrean/pagination, perubahan
kunci, audit/retry, keputusan bersamaan, row lock timeout, rollback saat gagal,
serta jumlah query yang dibatasi. Jalankan `mvn -Ppostgres-it clean install`
dengan environment database lokal `*_test` sesuai Step 2. Tidak ada API Gemini
atau database Supabase yang dipanggil test. Pemilihan soal `DISETUJUI` untuk
latihan ditambahkan pada Step 8 di bawah.

## Step 8 Strategi Latihan dan Mulai Sesi

`core` menyediakan `LatihanStrategy`, `AcakStrategy`, `BerwaktuStrategy`, dan
`FokusKelemahanStrategy` tanpa dependency Spring/persistence. Ketiganya menerima
iterator metadata kandidat unik, jumlah soal, waktu mulai, dan `RandomGenerator`
yang dapat diberi seed saat unit test. Hanya kandidat `DISETUJUI` yang dapat dipilih.

- **ACAK**: memilih subset dan urutan acak dari seluruh bank soal yang disetujui,
  lintas bagian dan pemilik materi, sesuai F5. Tidak membatasi kandidat pada halaman
  pertama; setiap kandidat mempunyai peluang yang sama.
- **BERWAKTU**: pemilihan sama dengan Acak, ditambah deadline sesi dari waktu server.
  Budget adalah jumlah soal yang benar-benar terambil × `LATIHAN_SECONDS_PER_QUESTION`
  (default 60, rentang 1–600 detik). `RencanaLatihan.sudahBerakhir` bernilai true
  tepat pada deadline dan sesudahnya. `selesai_at` tidak diisi saat sesi dimulai.
- **FOKUS_KELEMAHAN**: mendahulukan bagian dengan rasio salah/total jawaban tertinggi
  milik siswa yang sedang login. Bukan jumlah salah mentah. Perbandingan pecahan
  memakai `BigInteger` untuk menghindari pembulatan dan overflow; nilai sama diacak.
  Setelah soal bagian terlemah habis, lanjut bagian berikutnya. Bagian tanpa riwayat
  dianggap 0%; jika semua belum punya riwayat, pemilihan menjadi acak.

Endpoint **`POST /api/latihan/sesi`** memerlukan bearer JWT SISWA dan header
**`Idempotency-Key: <UUID-baru>`**. Token memverifikasi identitas; filter namespace,
method security, dan verifikasi role akun terkini membatasi otorisasi. Body hanya:

```json
{"mode":"FOKUS_KELEMAHAN","jumlahSoal":10}
```

`jumlahSoal` wajib 1–50. Field asing termasuk siswa/pemilik/status/kunci jawaban
ditolak. Jika bank memiliki lebih sedikit soal, sesi berisi seluruh soal yang
tersedia tanpa pengulangan. Jika tidak ada soal disetujui, respons `409` dengan
`NO_APPROVED_QUESTIONS` dan tidak ada sesi dibuat.

Response `201` memuat `sesiId`, `mode`, `mulaiAt`, `berakhirAt` (null untuk mode
tanpa timer), dan `soal[]`. Setiap soal berisi ID, ID bagian, teks, referensi gambar,
serta opsi berurutan yang hanya mempunyai ID/urutan/teks. **Kunci/is_benar tidak
dikirim maupun disimpan dalam snapshot publik sesi.** Riwayat fokus diambil lewat
`riwayat_jawaban → sesi_latihan.siswa_id`, sehingga riwayat siswa lain tidak ikut.
Tidak ada pembatasan kepemilikan materi pada bank soal yang sudah disetujui;
identitas pemilik sesi selalu berasal dari JWT, bukan input klien.

Retry dengan key, siswa, mode, dan jumlah yang sama mengembalikan snapshot sesi
yang sama (`201`), termasuk urutan soal dan deadline asli, walaupun bank/riwayat
sudah berubah. Deadline yang telah lewat tidak di-reset. Key yang sama dengan
mode/jumlah berbeda mendapat `409 IDEMPOTENCY_CONFLICT`. Key bersifat per siswa;
siswa lain tidak dapat mengambil sesi milik siswa pertama menggunakan key itu.
Gunakan UUID baru untuk sengaja memulai sesi baru.

Pemilihan membaca kandidat memakai PostgreSQL cursor dengan fetch size 128 dan
priority queue berukuran maksimal jumlah soal. Seluruh kandidat tetap diperiksa;
memori tidak tumbuh mengikuti besar bank. Query fokus mengagregasi jawaban siswa
sekali, memakai index siswa pada sesi dan index sesi pada riwayat yang sudah ada.
Teks/opsi hanya diambil untuk maksimal 50 ID terpilih lewat dua bulk query,
tanpa query per soal. SQL memakai schema aktual Hibernate agar test dan aplikasi
tidak salah membaca `public`. Waktu pemilihan tetap O(N log jumlahSoal); bank/riwayat
yang sangat besar dapat mencapai batas query dan mendapat respons retryable `503`.

User row lock menserialisasi start per siswa; unique index `(siswa_id,request_key)`
menjadi perlindungan tambahan. Sesi, snapshot, dan deadline ditulis atomik. Lock
wait dibatasi 2 detik, statement 5 detik, transaksi 10 detik. Kegagalan database
me-rollback sesi; ulangi dengan key sama. `400` untuk input/key tidak valid,
`401` tanpa autentikasi, `403` untuk MENTOR/akun yang sudah bukan SISWA,
`503 PRACTICE_BUSY` saat database sibuk, dan `500` untuk kegagalan penyimpanan.
Log terstruktur mencatat ID siswa/sesi, mode, jumlah, durasi request dan kategori
error, tanpa soal/opsi/token/key. Health menggunakan pemeriksaan DB Actuator yang
sudah ada; startup memvalidasi mapping dan migrasi.

V4 menambah metadata nullable pada `sesi_latihan`: `request_key`, `requested_count`,
`soal_snapshot` JSONB, dan `berakhir_at`. Jumlah tabel bisnis tetap sembilan.
Snapshot adalah dokumen historis publik, bukan tabel relasi baru. Sesi lama tetap
valid; CHECK menegakkan kelengkapan metadata, batas jumlah, bentuk/ukuran array,
dan deadline khusus BERWAKTU. Perubahan metadata memakai lock timeout 3 detik,
constraint `NOT VALID` lalu validasi, dan unique index `CONCURRENTLY`. Migrate ulang
menjadi no-op; partial apply dapat diperbaiki dengan repair/migrate setelah penyebab
gagal diperbaiki. Jangan mengedit V1–V3 yang sudah diterapkan.

Rollback `db/rollback/U4__practice_session.sql` dijalankan manual dengan request
start dihentikan, schema yang benar, dan setiap statement terpisah tanpa transaction
wrapper. Aman diulang pada metadata kosong dan mempertahankan sesi lama. Jika ada
snapshot aktif/tersimpan, rollback sengaja menolak agar soal/idempotency/deadline
tidak hilang; ekspor/pulihkan metadata melalui rencana pemeliharaan sebelum rollback.

Unit test memeriksa distribusi lintas bagian dengan seed tetap, status/jumlah/unik,
deadline aktual dan batas kedaluwarsa, persentase vs jumlah salah, fallback,
overflow/pecahan hampir sama, dan bagian terlemah di akhir iterator besar.
Integration test memakai PostgreSQL lokal terisolasi untuk role, agregasi per siswa,
snapshot tanpa jawaban, retry/konflik/konkurensi, rollback saat gagal, batas lock,
deadline yang tidak di-reset, serta penerapan ulang/rollback/constraint migrasi V4.
Jalankan `mvn -Ppostgres-it clean install` sesuai environment Step 2; test tidak
menggunakan Gemini atau Supabase. Endpoint menjawab soal, pencatatan jawaban, dan
evaluasi belum dibuat; validasi deadline saat menerima jawaban diterapkan bersama
endpoint jawaban pada step berikutnya, memakai `berakhir_at` server yang tersimpan.
